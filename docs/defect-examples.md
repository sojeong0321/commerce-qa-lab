# 결함 사례 기록

이 프로젝트를 만들면서 **실제로 발견한 결함**과, **테스트가 결함을 잡는지 검증하기 위해 의도적으로 주입한 결함**을 기록합니다.
모든 사례는 재현 절차와 증거를 포함합니다.

---

## 1. 실제로 발견한 결함

개발 중 검증 과정에서 발견해 수정한 것들입니다. 각 항목은 발견 경로가 다릅니다.

### D-001 수량 0 입력 시 요청이 전송되지 않고 이전 오류 메시지가 유지됨

| 항목 | 내용 |
|---|---|
| 발견 경로 | Phase 2 브라우저 수동 확인 |
| 재현 | 상품 목록 → 수량 칸에 `0` 입력 → "장바구니 담기" 클릭 |
| 기대 | 서버 검증 메시지 "수량(quantity)은 1 이상의 정수여야 합니다." 표시 |
| 실제 | 브라우저 기본 입력 검증(`min="1"`)이 submit을 차단 → 요청 미전송, 직전 오류 메시지가 그대로 남아 사용자가 혼란 |
| 원인 | 검증 주체가 브라우저와 서버로 이원화 |
| 수정 | form에 `novalidate` 적용, 서버를 단일 판단 주체로 |
| 회귀 방지 | `tests/api/cart.spec.ts` 수량 0/-1/1.5/"1"/"abc"/null 6종, E2E에서 서버 메시지 확인 |

### D-002 쿠폰 자동 해제 안내가 성공 메시지에 덮임

| 항목 | 내용 |
|---|---|
| 발견 경로 | Phase 3 브라우저 확인 |
| 재현 | 머그컵 3개(30,000원) + WELCOME5000 적용 → 수량을 2개로 변경 |
| 기대 | "최소 주문금액 미달로 쿠폰 적용을 해제했습니다" 안내 유지 |
| 실제 | 안내가 표시된 직후 "수량을 변경했습니다" 성공 메시지가 덮어써서, 할인이 소리 없이 사라진 것처럼 보임 |
| 원인 | 성공 메시지를 나중에 출력하는 순서 문제 |
| 수정 | 알림 우선순위 정리 (해제 사유가 있으면 성공 메시지 대신 표시) |
| 회귀 방지 | `tests/e2e/e2e-005-coupon-min-amount.spec.ts` |
| 배운 점 | 금액만 검증했다면 통과했을 결함. "사용자가 이유를 알 수 있는가"를 함께 봐야 잡힌다 |

### D-003 클라이언트 요청 오류가 서버 오류(500)로 응답됨

| 항목 | 내용 |
|---|---|
| 발견 경로 | 중간 점검(코드 리뷰 + 재현) |
| 재현 | `POST /api/cart/items`에 100KB 초과 본문 전송 |
| 기대 | 4xx + `VALIDATION_ERROR` |
| 실제 | `500 INTERNAL_ERROR` (body-parser의 413 오류를 미처리) |
| 영향 | 사용자 실수가 서버 장애로 집계되어 모니터링·알람 신뢰도 저하 |
| 수정 | errorHandler에서 4xx 계열 오류를 클라이언트 오류로 매핑 |
| 회귀 방지 | `tests/unit/app.test.js` "본문이 너무 크면 서버 오류(500)가 아니라 요청 오류로 답한다" |

### D-004 품절 상품의 장바구니 수량을 줄일 수 없음

| 항목 | 내용 |
|---|---|
| 발견 경로 | 중간 점검 |
| 재현 | 러닝화 2개 담기 → 다른 사용자가 전량 구매 → 수량을 1로 변경 |
| 기대 | 수량 감소는 허용 (재고를 더 요구하지 않는 안전한 조작) |
| 실제 | `409 OUT_OF_STOCK`. 삭제 외에는 장바구니를 정리할 방법이 없음 |
| 수정 | 수량을 늘릴 때만 재고 검증 |
| 회귀 방지 | `tests/api/cart.spec.ts` "담아 둔 사이 품절되어도 수량을 줄일 수는 있다" |

### D-005 주문 실패 후 주문 버튼이 비활성 상태로 고정됨

| 항목 | 내용 |
|---|---|
| 발견 경로 | 중간 점검(네트워크 차단 시뮬레이션) |
| 재현 | 장바구니 → 네트워크 차단 → "주문하기" 클릭 → 네트워크 복구 |
| 기대 | 오류 안내 후 버튼 재활성화 |
| 실제 | 버튼이 비활성으로 남아 새로고침 전까지 주문 불가. 오류 메시지도 브라우저 원문("Failed to fetch") |
| 수정 | `finally`로 버튼 상태 복구, 네트워크 오류를 한국어 안내로 변환 |
| 회귀 방지 | 브라우저 확인 스크립트(요청 1회 차단 후 재시도 성공 확인) |

### D-006 목록 요소의 접근 이름 중복으로 테스트가 대상을 특정하지 못함

| 항목 | 내용 |
|---|---|
| 발견 경로 | 중간 점검(로케이터 검증) |
| 재현 | `getByLabel('수량')` → 3개 매칭 / `getByTestId('order-total')` → 주문 2건에서 strict mode 위반 / `getByRole('link', { name: '장바구니', exact: true })` → 0개 |
| 원인 | 수량 입력 라벨이 모두 "수량", 장바구니 링크 접근 이름에 개수 숫자가 포함 |
| 수정 | 라벨에 상품명 포함("머그컵 수량"), 링크에 `aria-label`, 개수 span에 `aria-hidden` |
| 영향 | 애플리케이션 버그는 아니지만, 그대로 두면 E2E 작성 자체가 불가능했음 |

## 2. 테스트 검증을 위해 주입한 결함 (Mutation Testing)

"테스트가 통과한다"는 사실만으로는 테스트가 제 역할을 한다고 말할 수 없습니다.
코드를 의도적으로 망가뜨려 **테스트가 실패하는지** 확인했습니다. 모든 주입은 확인 후 즉시 원복했습니다.

### 중간 점검 시점: 77개 테스트가 통과하는데 6종의 결함을 검출하지 못함

| 주입한 결함 | 결과(당시) | 보강 후 |
|---|---|---|
| 주문 시 첫 상품만 재고 차감 | 통과(미검출) | 3건 실패 |
| 취소 시 첫 상품만 재고 복구 | 통과 | 2건 실패 |
| 주문 항목을 1건만 저장 | 통과 | 2건 실패 |
| 장바구니 수량 합산 제거 | 통과 | 4건 실패 |
| 수량 변경 시 재고 검증 제거 | 통과 | 3건 실패 |
| `X-User-Id` 검증 무력화 | 통과 | 8건 실패 |
| 모든 AppError를 400으로 응답 | 통과 | 16건 실패 |
| 타 사용자의 동일 쿠폰까지 USED 처리 | 통과 | 2건 실패 |
| 주문/취소 트랜잭션 제거 | 통과 | 각각 실패 |

**근본 원인 2가지**
1. 성공하는 다중 상품 주문 케이스가 없어 반복 처리의 첫 항목만 검증되고 있었음
2. 대부분의 테스트가 서비스 함수를 직접 호출해, HTTP 계층(인증·상태 코드 전달)이 미검증

**조치:** 테스트 48개 추가 (장바구니 규칙 15, 다중 상품 주문·취소, 사용자별 쿠폰 구분, 트랜잭션 롤백, HTTP 계층 30)

### API 테스트 검증 (Phase 5): 8종 전부 검출

재고 미차감(11건 실패) · 재고 미복구(3) · 중복 취소 허용(2) · 쿠폰 최소금액 무시(2) · 쿠폰 재사용 허용(2) · 재고 초과 허용(5) · 타인 주문 접근 허용(2) · 수량 검증 제거(7)

### E2E 테스트 검증 (Phase 6): 6종 전부 검출

재고 미복구(E2E-003) · 쿠폰 미사용 처리(2) · 할인 미적용(3) · 재고 초과 허용(2) · 장바구니 미초기화(2) · 재고 표시 오류(4)

## 3. CI 실패 시나리오 검증 (Phase 7·8)

의도적 결함을 담은 브랜치로 Pull Request를 생성해, CI가 결함을 검출하고 증거를 남기는지 확인했습니다.

| 항목 | 내용 |
|---|---|
| PR | #1 `[DEMO] 의도적 결함: 주문 취소 시 재고 미복구` (병합하지 않고 종료) |
| 주입 | `app/services/orderService.js` 취소 처리에서 재고 복구 제거 |
| 검출 | Unit 4건 · API 3건 · E2E 1건 실패 → workflow 실패 |
| 확보한 증거 | `test-failed-1.png`, `trace.zip`, `error-context.md`, API/E2E HTML 리포트 |
| E2E 실패 메시지 | `Expected: "재고 3개" / Received: "재고 2개"` (러닝화 재고 표시) |

### 이 검증에서 발견한 CI 설정 문제

첫 실행에서는 **증거가 전혀 수집되지 않았습니다.** Unit 테스트가 먼저 실패하자 이후 단계가 건너뛰어져, Playwright가 실행되지 않았기 때문입니다.

- **수정:** 앞 단계가 실패해도 모든 테스트 레이어를 실행하도록 변경(`if: ${{ !cancelled() }}`). workflow는 여전히 실패로 표시됩니다.
- **효과:** 어느 레이어까지 영향을 받았는지 한 번에 파악할 수 있고, E2E 증거도 확보됩니다.
- **트레이드오프:** 전체 실행이 1분이라 비용이 낮아 선택한 구성입니다. 실행이 긴 프로젝트라면 fail-fast가 더 적절할 수 있습니다.

## 결함 리포트 작성 기준

이 문서의 각 항목은 실무 결함 리포트와 같은 요소를 갖추고 있습니다.

1. **재현 절차** — 누구나 같은 순서로 재현 가능
2. **기대 결과와 실제 결과** — 무엇이 잘못인지 명확히
3. **증거** — 스크린샷, 트레이스, 실패 메시지
4. **원인** — 추정이 아니라 확인한 원인
5. **수정과 회귀 방지** — 고친 내용과, 재발 시 잡아낼 테스트
