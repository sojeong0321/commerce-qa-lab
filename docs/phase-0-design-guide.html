commerce-qa-lab, 무엇을 만들고 어떻게 검사하는가

코딩을 몰라도 읽을 수 있게 쉬운 말과 비유로 정리했습니다. 이 문서는 "앞으로 무엇을 만들지"를 설명하는 설계도이고, 아직 만든 것은 없습니다.

한 줄 요약: 작은 온라인 쇼핑몰을 직접 만든 다음, 그 쇼핑몰이 제대로 동작하는지 검사 로봇(자동화 테스트)이 매번 대신 확인하게 만드는 프로젝트입니다.
작성일 2026-09-22현재 단계: 설계 (Phase 0 / 10)
왜 만드나

손으로 하던 검사를 로봇에게 맡기는 연습

지금까지 해 온 수동 QA는 사람이 직접 화면을 눌러 보며 "잘 되나?"를 확인하는 일입니다. QA 자동화 엔지니어는 그 확인 과정을 프로그램으로 적어 두고 컴퓨터가 반복하게 만듭니다. 채용 담당자에게 "이걸 실제로 할 줄 안다"는 걸 보여 주려면 진짜로 돌아가는 결과물이 있어야 합니다.

지금 (수동 QA)
  • 사람이 매번 쇼핑몰에 들어가 클릭
  • 100개를 확인하려면 몇 시간
  • 피곤하면 놓치는 게 생김
목표 (자동화 QA)
  • 확인할 내용을 한 번 적어 두면 로봇이 반복
  • 100개를 몇 분 안에 확인
  • 매번 똑같이 꼼꼼하게, 실패하면 증거 사진도 남김

검사할 대상이 없으면 검사를 보여 줄 수 없습니다. 그래서 검사 대상이 될 작은 쇼핑몰부터 직접 만듭니다. 남이 만든 연습용 사이트를 쓰지 않고 직접 만드는 이유는, 쇼핑몰 규칙을 우리가 정해야 "규칙대로 동작하는지"를 정확히 검사할 수 있기 때문입니다.

무엇을 만드나 ①

작은 쇼핑몰: 손님이 하는 일

보통 온라인 쇼핑몰과 같습니다. 손님은 아래 순서로 움직입니다.

1상품 보기진열대에서 가격과 남은 수량 확인
2장바구니담고, 개수 바꾸고, 빼기
3쿠폰할인 쿠폰 적용
4주문결제 금액 확인 후 주문 완료
5취소주문 내역에서 취소

진열대에 올릴 상품도 미리 정해 두었습니다. 머그컵(1만 원), 데님 팬츠(3만5천 원), 러닝화(8만9천 원), 품절된 에코백, 판매 중지된 모자. 테스트할 때 이 상품들이 항상 똑같은 상태로 준비됩니다.

무엇을 만드나 ②

가게 규칙: 로봇이 지켜보는 약속들

테스트의 본질은 "정해진 규칙대로 동작하는가"를 확인하는 일입니다. 이 쇼핑몰의 규칙은 아래와 같습니다.

상품

재고가 0이면 살 수 없다

품절된 에코백은 장바구니에 담기지 않아야 합니다.

장바구니

남은 개수보다 많이 담을 수 없다

데님 팬츠가 5개 남았으면 6개는 거절해야 합니다.

쿠폰

3만 원 이상일 때만 5천 원 할인

딱 3만 원이면 되고, 2만 원이면 안 됩니다.

쿠폰

한 번 쓴 쿠폰은 다시 못 쓴다

같은 쿠폰으로 두 번째 주문을 하면 거절해야 합니다.

주문

주문하면 재고가 줄어든다

러닝화 3개 중 1개를 사면 남은 수량이 2개로 바뀌어야 합니다.

주문

하나라도 부족하면 주문 전체가 취소된다

일부만 주문되고 나머지는 실패하는 어정쩡한 상태가 생기면 안 됩니다.

취소

취소하면 재고가 원래대로 돌아온다

2개로 줄었던 러닝화가 취소 후 다시 3개가 되어야 합니다.

취소

같은 주문을 두 번 취소할 수 없다

두 번째 취소는 거절하고, 재고가 두 번 늘어나면 안 됩니다.

새로 정한 정책

주문을 취소하면 쿠폰을 돌려준다

과제에서 "직접 정하라"고 한 부분입니다. 손님 입장에서 자연스럽고 실제 쇼핑몰에서도 흔한 방식이라 "돌려준다"로 정했습니다. 취소 후 같은 쿠폰으로 다시 주문할 수 있어야 합니다.

어떻게 검사하나

검사를 세 층으로 나눕니다

자동차 공장에 비유하면 이해하기 쉽습니다. 부품 검사는 빠르니까 아주 많이 하고, 도로 주행 시험은 오래 걸리니까 꼭 필요한 것만 합니다. 이 모양을 업계에서는 테스트 피라미드라고 부릅니다.

E2E실제 손님처럼

로봇이 진짜 인터넷 창(브라우저)을 열고 손님처럼 클릭하고 입력합니다. 가장 현실적이지만 느리기 때문에 중요한 쇼핑 흐름 5가지만 검사합니다.

예: 상품 담기 → 쿠폰 적용 → 주문 → 화면에 "30,000원" 표시 확인

API뒷문으로 직접 주문서 넣기

화면을 거치지 않고 가게 시스템에 직접 요청을 보냅니다. 화면을 그릴 필요가 없어서 빠르고, 온갖 까다로운 경우를 여기서 꼼꼼하게 검사합니다.

예: 수량에 0, -1, 1.5, "abc"를 넣으면 전부 거절하는지 확인

Unit부품 하나 검사

할인 금액 계산 같은 작은 부품 하나만 떼어 검사합니다. 1초도 걸리지 않습니다.

예: 29,999원이면 할인 없음, 30,000원이면 할인 적용

왜 API와 E2E를 나누나요? 모든 경우를 브라우저로 검사하면 느리고, 화면 로딩이 조금만 늦어도 검사가 괜히 실패하기 쉽습니다. 그래서 "규칙이 맞는가"는 빠른 API 검사가 맡고, "손님이 화면에서 실제로 쇼핑을 끝낼 수 있는가"는 E2E가 맡도록 역할을 나눴습니다.

검사 예시

로봇이 실제로 확인하는 것들

핵심은 "성공했다"는 대답만 믿지 않고 결과까지 확인하는 것입니다. 주문이 성공했다고 나와도 재고가 실제로 줄었는지, 쿠폰이 실제로 사용 처리됐는지까지 다시 들여다봅니다.

상황기대하는 결과함께 확인하는 뒷정리
데님 팬츠 2개 주문주문 성공재고 5 → 3, 장바구니 비워짐
머그컵 3개(딱 30,000원)에 쿠폰할인 적용결제금액 25,000원
머그컵 2개(20,000원)에 쿠폰거절 "3만 원 이상"할인 0원, 쿠폰은 그대로
이미 쓴 쿠폰으로 또 주문거절 "이미 사용"두 번째 주문이 생기지 않음
주문 취소취소 완료재고 원래대로, 쿠폰 다시 사용 가능
같은 주문 두 번째 취소거절 "이미 취소됨"재고가 두 번 늘지 않음
러닝화 3개를 담아 둔 사이 다른 손님이 2개 구매거절 "재고 부족"재고·쿠폰·장바구니 모두 그대로
없는 주문 번호로 취소거절 "주문 없음"—

표의 "딱 30,000원" 같은 경계 지점을 일부러 검사하는 것을 경계값 테스트라고 합니다. 버그가 가장 잘 숨는 곳이 이런 경계입니다.

공정한 시험

매 검사는 같은 출발선에서 시작합니다

앞 검사에서 러닝화를 사 버리면 다음 검사는 재고 2개에서 시작하게 되고, 결과가 검사 순서에 따라 달라집니다. 이를 막으려고 검사 하나를 시작할 때마다 가게를 처음 상태로 되돌립니다. 진열대, 쿠폰, 장바구니가 전부 초기화됩니다.

이 "초기화 버튼"이 실제 운영 중인 가게에 있으면 큰 사고가 납니다. 그래서 검사 모드에서만 존재하게 만들고, 일반 모드에서는 없다는 것도 따로 검사합니다.

자동 실행 (CI)

코드를 올릴 때마다 로봇이 알아서 전부 검사합니다

코드를 GitHub(코드 보관소)에 올리면 GitHub Actions라는 기능이 자동으로 아래 순서대로 검사를 돌립니다. 사람이 버튼을 누를 필요가 없습니다.

준비물 설치→ 가게 문 열기→ 부품 검사 (Unit)→ 뒷문 검사 (API)→ 손님 검사 (E2E)→ 보고서
전부 통과하면 초록불새로 바꾼 코드가 기존 기능을 망가뜨리지 않았다는 뜻입니다.
하나라도 실패하면 빨간불어디서 실패했는지 바로 보이고, 문제가 있는 코드가 그대로 통과되지 않습니다.
실패의 증거

실패하면 "왜 실패했는지" 증거가 남습니다

"안 돼요"만으로는 개발자가 고칠 수 없습니다. 수동 QA에서 버그 리포트에 캡처를 붙이던 것처럼, 로봇도 증거를 자동으로 남깁니다. 이 증거는 GitHub에서 파일로 내려받을 수 있습니다.

원칙쉬운 말로
진짜로 동작하는 것만설명서에만 있고 실제로 없는 기능은 만들지 않습니다.

재시도로 숨기지 않기가끔 실패하는 검사를 여러 번 다시 돌려 통과시키지 않고, 원인을 찾아 고칩니다.

진행 순서

11단계로 나눠서 하나씩 완성합니다

  1. 0
    설계
    무엇을 만들지, 어떻게 검사할지 정하기 (이 문서)
  2. 1
    가게 뼈대 + 데이터 창고
    서버를 켜고, 상품·손님 정보를 저장할 곳 만들기
  3. 2
    상품 · 장바구니
    진열대와 장바구니 화면, 재고 규칙
  4. 3
    쿠폰
    할인 계산, 최소 금액, 사용 여부
  5. 4
    주문 · 취소 · 재고
    주문하면 재고 감소, 취소하면 복구
  6. 5
    API 자동 검사
    뒷문 검사 약 30개 작성
  7. 6
    E2E 자동 검사
    브라우저로 손님 흐름 5개 작성
  8. 7
    자동 실행 (CI)
    코드를 올리면 GitHub가 검사를 자동으로 실행
  9. 8
    실패 증거 · 보고서
    일부러 버그를 넣어 증거가 제대로 남는지 확인
  10. 9
    문서 정리
    채용 담당자용 README와 설명 문서
  11. 10
    최종 점검
    전체 검사를 다시 돌리고, 설계와 실제 결과 비교

다음 단계 전에 정해 둔 세 가지

제가 추천하는 방향으로 정해 두었습니다. 다르게 하고 싶으면 말씀해 주세요.

주문을 취소하면 쿠폰을 돌려줄까요?

추천: 돌려준다

손님 입장에서 자연스럽고, 실제 쇼핑몰에서도 흔한 방식입니다.

로그인 기능을 만들까요?

추천: 만들지 않는다 (손님 번호로만 구분)

로그인은 이번 검사의 주제가 아니라서, 복잡도만 늘리고 배울 점은 적습니다. 손님 두 명(Alice, Bob)을 미리 만들어 두고 번호로 구분합니다.

검사를 동시에 여러 개 돌릴까요?

추천: 한 번에 하나씩 순서대로

가게 장부가 하나라서, 동시에 돌리면 서로의 검사를 방해합니다. 검사가 약 50개 정도라 순서대로 돌려도 몇 분이면 끝납니다.

Phase 0 설계가 끝났습니다. 괜찮으면 Phase 1(가게 뼈대 + 데이터 창고)부터 실제로 만들기 시작합니다.
