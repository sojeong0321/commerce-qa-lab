새로 쓴 문서

설계 때 약속했던 문서 4종

테스트 전략

왜 이렇게 나눴는가

레이어별 책임과 배분 기준, E2E를 늘리지 않는 이유, 데이터 전략, 실행 정책(동시 실행 안 함·재시도 안 함)과 그 근거, 다루지 않는 범위까지.

테스트 케이스

규칙 ↔ 테스트 연결

비즈니스 규칙 21개를 테스트와 이어 붙인 표입니다. "이 규칙은 어느 테스트가 보나요?"에 즉시 답할 수 있습니다. 모든 규칙이 최소 2개 층에서 검증됩니다.

아키텍처

구조와 선택의 이유

계층 책임, 스키마 설계 원칙(품절을 저장하지 않는 이유, 주문 스냅샷), 트랜잭션 경계, 에러 코드 체계, 기술 선택 근거.

결함 사례

실제로 찾은 결함

발견 경로가 서로 다른 6건 + 주입 결함 23종. 재현 절차·기대/실제·증거·원인·회귀 방지를 모두 갖춘 형식입니다.

문서 원칙

지킨 것

원칙구체적으로
없는 기능을 쓰지 않는다README는 "지금 실제로 동작하는 것만" 적습니다. 예정 항목은 "예정"으로 표시합니다
숫자는 실행 결과에서 가져온다테스트 개수, 실행 시간, CI 소요 시간 모두 실측값입니다
선택의 이유를 남긴다"동시 실행하지 않음" 같은 결정마다 근거와 트레이드오프를 함께 적습니다
실패와 실수도 기록한다테스트가 버그를 못 잡던 일, CI에서 증거가 안 남던 일, 되돌리기 명령으로 작업을 날린 일까지
재현되지 않은 것은 그렇게 쓴다점검에서 나온 지적 중 재현 실패한 항목은 "재현되지 않음"으로 남겼습니다

포트폴리오에서 실패를 기록한 문서가 성공만 나열한 문서보다 신뢰를 얻습니다. "테스트 205개 통과"보다 "테스트 77개가 통과하는데 9종의 결함을 못 잡고 있었고, 그걸 어떻게 발견해서 고쳤는지"가 QA 역량을 더 잘 보여 줍니다.
