QA 관점 1

"성공했다"는 응답만 믿지 않는다

이 프로젝트의 검사는 응답 확인에서 멈추지 않습니다. 예를 들어 "여러 상품 중 하나만 재고가 부족한 주문"을 확인할 때는 네 가지를 더 봅니다.

거절됐는가

상태 코드 409와 이유 코드가 약속대로 오는가

다른 상품 재고는?

부족하지 않았던 상품의 재고가 그대로인가

쿠폰은?

실패한 주문에서 쿠폰이 소모되지 않았는가

장바구니와 주문 내역은?

장바구니가 유지되고, 주문이 생기지 않았는가

상태 확인은 데이터베이스를 직접 열어 보지 않고 공개 조회 API로 합니다. 손님이 볼 수 있는 방식으로만 확인하기 때문에, 내부 구조가 바뀌어도 검사가 깨지지 않습니다.

QA 관점 2

검사끼리 서로 방해하지 않는다

자동화에서 가장 흔한 함정은 "앞 검사가 남긴 흔적 때문에 뒤 검사가 실패"하는 것입니다. 이걸 막기 위해 세 가지를 확인했습니다.

확인 방법결과
3번 연속 전체 실행73개 통과 × 3
파일을 하나씩 따로 실행5개 파일 모두 단독으로 통과
실행을 둘로 쪼개서 실행51개 + 22개 모두 통과

검사는 한 번에 하나씩 순서대로 실행합니다. 데이터베이스가 하나뿐이라 동시에 돌리면 서로의 데이터를 건드리기 때문입니다. 속도보다 언제 돌려도 같은 결과를 택한 것이고, 73개가 4초에 끝나므로 손해도 없습니다. 나중에 속도가 문제가 되면 검사별로 DB를 나누는 방법이 있습니다.
