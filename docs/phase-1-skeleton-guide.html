Phase 1 · 완료

가게 문을 열고, 장부를 만들었다

검사할 대상이 있어야 검사를 만들 수 있습니다. 이 단계에서는 상품도 화면도 없이, 가게 건물과 장부만 세웠습니다.

한 줄 요약: 서버(가게)를 켜고 끌 수 있게 만들고, 데이터베이스(장부)를 언제든 처음 상태로 되돌리는 기능을 붙였습니다.
만든 것

이 단계에서 실제로 동작하는 것

서버

가게를 켜고 끌 수 있다

평소용과 검사용, 두 가지 모드로 켤 수 있습니다. 검사용은 켤 때마다 장부를 처음 상태로 되돌립니다.

창고

장부(DB) 테이블 7개

손님, 상품, 장바구니, 쿠폰, 보유 쿠폰, 주문, 주문 상품. 설계서에서 정한 그대로입니다.

초기 데이터

항상 똑같은 출발선

손님 2명(Alice, Bob), 상품 5개, 쿠폰 2종, 손님에게 나눠 준 쿠폰 3장이 미리 들어갑니다.

초기화

처음 상태로 되돌리기

검사 하나를 시작할 때마다 부르는 기능입니다. 검사끼리 서로 방해하지 않게 해 줍니다.

API

상태 확인과 손님 목록

가게가 살아 있는지 묻는 주소와, 손님 목록을 주는 주소 두 개를 만들었습니다.

에러

거절할 때도 이유를 준다

없는 주소나 깨진 요청에는 이유 코드와 설명을 담아 돌려줍니다. 이 형식은 이후 모든 기능이 그대로 따릅니다.

중요한 결정

초기화 기능은 검사 모드에만 존재한다

장부를 통째로 되돌리는 기능은 검사에는 꼭 필요하지만, 진짜 영업 중인 가게에 있으면 사고가 납니다. 그래서 검사 모드로 켰을 때만 그 주소가 만들어지고, 평소 모드에서는 아예 존재하지 않게 했습니다.

이런 "테스트 전용 뒷문"은 실무에서도 자주 쓰이지만, 운영 환경에 실수로 열려 있어 사고가 나는 대표적인 지점입니다. 그래서 평소 모드에서 이 주소가 없는지 확인하는 검사를 따로 만들어 두었습니다.

검사 결과

13개 검사, 3번 연속 통과

13자동 검사 개수
3회연속 실행 통과
0실패
확인한 것왜 확인했나
초기화를 두 번 해도 완전히 같은 상태검사가 항상 같은 출발선에서 시작하는지가 자동화의 기본 조건입니다.
데이터를 바꾼 뒤 초기화하면 원래대로앞 검사가 남긴 흔적이 다음 검사에 영향을 주면 안 됩니다.
재고를 음수로 저장하면 장부가 거부프로그램이 실수해도 장부 자체가 마지막 방어선이 됩니다.
평소 모드에는 초기화 주소가 없음위에서 정한 안전 규칙이 실제로 지켜지는지 확인합니다.
없는 주소, 깨진 요청에 대한 응답 형식이유를 알려 주는 방식이 처음부터 일정해야 합니다.
검사를 믿을 수 있나

일부러 버그를 넣어 봤습니다

"통과"만 봐서는 검사가 제대로 동작하는지 알 수 없습니다. 그래서 초기화 주소가 모든 모드에서 열리도록 코드를 일부러 망가뜨려 봤습니다.

결과: 해당 검사 2개가 정확히 실패로 잡아냈습니다. 확인 후 코드는 원래대로 되돌렸습니다. 이렇게 "검사가 실패할 줄 아는지" 확인하는 습관이 가짜 통과를 막아 줍니다.

직접 해 보기

내 컴퓨터에서 실행하는 방법

npm install      # 필요한 준비물 설치
npm run db:setup # 장부 만들고 초기 데이터 넣기
npm start        # 가게 켜기
npm run test:unit # 자동 검사 돌려 보기

가게를 켠 뒤 브라우저에서 http://localhost:3000/api/health 를 열면 {"status":"ok"} 가 보입니다. 이 단계에서는 아직 화면이 없습니다.
