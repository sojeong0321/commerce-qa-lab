Phase 10 · 완료 · 프로젝트 종료

다 끝났다고 생각한 뒤에 15가지를 더 찾았다

마지막 점검에서 가장 뼈아픈 것이 나왔습니다. Phase 8에서 "실패 증거를 남긴다"고 적어 둔 바로 그 기능이, 실제로는 증거를 지우고 있었습니다.

한 줄 요약: 검사 206개 통과로 프로젝트를 마칩니다. 마지막 점검에서 반드시 고쳐야 할 5건을 포함해 15가지를 수정했습니다.
가장 중요한 발견

증거를 남기는 기능이 증거를 지우고 있었다

최종 점검에서 발견

E2E 검사가 시작되면서 API 검사의 증거를 삭제했다

검사 결과물은 모두 같은 폴더에 저장되는데, Playwright는 실행을 시작할 때 그 폴더를 비웁니다. 즉 API 검사가 실패해 증거를 남겨도, 바로 뒤이어 실행되는 E2E 검사가 그것을 지워 버렸습니다.

확인 방법: API 실패 증거를 흉내 낸 파일을 두고 E2E를 실행했더니 사라졌습니다.

고친 방법: 검사 종류별로 결과 폴더를 나눴습니다(test-results/api, test-results/e2e). 보고서는 이미 나눠 두었는데 증거 폴더를 빠뜨렸던 것입니다.

왜 중요한가: Phase 8 문서에는 "모든 레이어의 증거를 확보한다"고 적혀 있었습니다. 문서가 사실이 아닌 상태였고, 면접에서 "CI에서 실패한 API 트레이스를 보여 달라"는 요청이 오면 바로 드러났을 문제입니다.

검사 개수가 계획의 5배가 된 것은 계획이 틀려서가 아니라 검증하면서 배웠기 때문입니다. "상품 2개 이상 주문 성공 케이스가 없어서 반복 처리의 첫 항목만 검사되고 있었다" 같은 사실은 실제로 코드를 망가뜨려 보기 전에는 알 수 없었습니다.

돌아보며

이 프로젝트가 보여 주는 것

통과 개수는 품질이 아니다

77개가 통과하는데 9종의 결함을 못 잡던 시점이 있었습니다. 검사가 제 역할을 하는지는 망가뜨려 봐야 압니다.

결과가 아니라 뒷정리까지 본다

"거절됐다"만 확인하면 절반입니다. 재고·쿠폰·장바구니가 그대로인지까지 봐야 합니다.

검사하기 좋게 만드는 것도 일이다

화면 요소의 이름, 경계값이 나오는 초기 데이터, 초기화 기능을 설계 단계에서 준비했습니다.

문서는 검증 대상이다

최종 점검에서 나온 문제의 절반이 "문서가 사실과 다름"이었습니다.

실수도 기록한다

되돌리기 명령으로 작업을 날린 일, 증거가 안 남던 일까지 남겼습니다.

"완성"이라고 선언한 뒤의 점검에서 가장 중요한 문제가 나왔습니다.

프로젝트를 마칩니다. 전체 요약은 진행 현황, 저장소 첫 화면 설명은 README.md, 상세 문서는 docs/ 폴더의 test-strategy · test-cases · architecture · defect-examples에 있습니다.
