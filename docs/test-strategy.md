# 테스트 전략

## 1. 목표

이 프로젝트의 테스트는 두 가지를 증명하기 위해 존재합니다.

1. 정의된 비즈니스 규칙이 **실제로 지켜지는가**
2. 규칙이 깨졌을 때 **테스트가 그것을 잡아내는가**

두 번째가 첫 번째보다 중요합니다. 통과하는 테스트 개수는 품질을 보장하지 않습니다. 실제로 이 프로젝트는 테스트 77개가 모두 통과하는 상태에서 9종의 결함을 검출하지 못하고 있었습니다([중간 점검](phase-4-5-review-guide.html)).

## 2. 테스트 피라미드

```
        ▲  E2E 7            실제 브라우저 · 핵심 사용자 여정 5
      ▲▲▲  API 73           실제 HTTP · 비즈니스 규칙과 엣지 케이스
    ▲▲▲▲▲  Unit/서비스 125  순수 계산 · DB 상태 전이 · HTTP 계약
```

| 레이어 | 개수 | 실행 시간 | 도구 | 책임 |
|---|---|---|---|---|
| 순수 함수 | 38 | < 0.3s | `node:test` | 금액 계산, 경계값, 입력 검증 |
| 서비스 + DB | 57 | < 0.3s | `node:test` + in-memory SQLite | 재고·쿠폰·주문 상태 전이, 트랜잭션 롤백 |
| HTTP 계약 | 30 | < 0.5s | `node:test` + `app.listen(0)` | 인증 401, 상태 코드 매핑, 에러 응답 형식 |
| API | 73 | ~4s | Playwright `request` | 실제 서버 대상 규칙 검증 + 상태 부작용 |
| E2E | 7 | ~5s | Playwright (Chromium) | 사용자 여정 완주 가능 여부 |

### 레이어 배분 기준

**API에서 검증하는 것**
- 비즈니스 규칙의 모든 분기 (재고, 쿠폰, 주문, 취소)
- 동등 분할과 경계값 (수량 0/-1/1.5/문자열, 금액 29,999/30,000/30,001)
- 실패 시 상태 불변 검증
- 인증·권한 (타 사용자 리소스 접근)

**E2E에서만 검증하는 것**
- 화면 간 이동이 있어야 성립하는 흐름 (상품 → 장바구니 → 주문 → 완료 → 내역)
- 화면 표시와 서버 상태의 일치 (재고 표시, 결제금액, 상태 배지)
- 사용자가 이유를 알 수 있는가 (거절 사유 노출, 쿠폰 자동 해제 안내)

**E2E에서 검증하지 않는 것**
- 입력값 검증 전수 — API에서 이미 검증
- 권한 분기 — API에서 이미 검증
- 모든 실패 케이스 조합 — 대표 케이스만

E2E를 늘리지 않는 이유는 느려서만이 아닙니다. 화면 구조 변경에 취약해 유지보수 비용이 빠르게 증가하고, 실패했을 때 원인 범위가 넓어 디버깅이 느려집니다.

## 3. 테스트 데이터 전략

### 결정적 초기 데이터

`app/db/seed.js`에 고정된 초기 데이터를 두고, 모든 테스트가 같은 출발선에서 시작합니다.

| 상품 | 가격 | 재고 | 상태 | 테스트에서의 역할 |
|---|---|---|---|---|
| 머그컵 | 10,000 | 20 | ACTIVE | 3개 = 정확히 30,000원 → 쿠폰 경계값 |
| 데님 팬츠 | 35,000 | 5 | ACTIVE | 기본 주문, 재고 초과 |
| 러닝화 | 89,000 | 3 | ACTIVE | 적은 재고 → 경합 시나리오 |
| 에코백 | 15,000 | **0** | ACTIVE | 품절 |
| 단종 모자 | 20,000 | 10 | **INACTIVE** | 판매 중지 |

**테스트하기 좋은 데이터를 설계하는 것도 QA의 일입니다.** 머그컵 가격을 10,000원으로 정한 이유는 3개를 담으면 쿠폰 최소 주문금액(30,000원)과 정확히 같아져, 경계값을 UI에서도 재현할 수 있기 때문입니다.

### 초기화 방식

- 모든 테스트는 시작 전에 `POST /api/test/reset` 호출 (Playwright fixture가 자동 수행)
- 단위/서비스 테스트는 테스트마다 새로운 in-memory DB 생성
- 이 엔드포인트는 `NODE_ENV=test`에서만 등록되며, 다른 환경에서 404인지 확인하는 테스트가 있음

### 독립성 검증

테스트가 순서에 의존하지 않는지 세 가지 방법으로 확인했습니다.

| 방법 | 결과 |
|---|---|
| 3회 연속 전체 실행 | 통과 |
| 파일 단독 실행 (10개 파일) | 전부 통과 |
| 샤드 분할 실행 (`--shard=1/2`, `2/2`) | 통과 |

## 4. 실행 정책

| 설정 | 값 | 근거 |
|---|---|---|
| `workers` | 1 | DB가 단일 파일이라 병렬 실행 시 상호 간섭. 전체가 9초라 손해가 작음 |
| `fullyParallel` | false | 동일 |
| `retries` | 0 | 불안정한 테스트를 재시도로 은폐하지 않음 |
| `trace` | `retain-on-failure` | 재시도가 없으므로 `on-first-retry`는 무의미 |
| `screenshot` | `only-on-failure` | 용량 관리 |
| `webServer` | `npm run start:test` | 테스트가 앱을 직접 기동. 로컬과 CI 동작이 동일 |

**병렬 실행이 필요해지면:** worker별로 DB 파일과 포트를 분리하는 방식으로 전환할 수 있습니다. 현재 규모에서는 불필요한 복잡도라 선택하지 않았습니다.

## 5. 검증 원칙

### 상태 부작용까지 검증한다

응답 코드만 확인하는 테스트는 절반만 검증한 것입니다. 이 프로젝트의 테스트는 실패 케이스마다 다음을 함께 확인합니다.

- 재고가 변하지 않았는가
- 쿠폰이 소모되지 않았는가
- 장바구니가 유지되는가
- 주문이 생성되지 않았는가

예: "다중 상품 주문 중 하나만 재고 부족" 테스트는 거절 확인 외에 **부족하지 않았던 상품의 재고까지** 검증합니다. 트랜잭션 원자성은 이 검증으로만 드러납니다.

### 블랙박스로 확인한다

API·E2E 테스트는 상태 확인에 DB를 직접 조회하지 않고 공개 조회 API를 사용합니다. 내부 스키마가 바뀌어도 테스트가 깨지지 않고, 사용자가 실제로 볼 수 있는 값으로 검증하게 됩니다.
서비스 단위 테스트는 예외적으로 in-memory DB를 직접 확인합니다(그 계층의 책임 범위이기 때문).

### 안정적인 로케이터

우선순위: `getByRole` → `getByLabel` → `getByTestId`

- 고정 대기(`waitForTimeout`)와 XPath 사용 0건
- 목록 내부 요소는 카드/행으로 범위를 좁힌 뒤 조회
- 화면 설계 단계에서 접근 가능한 이름을 먼저 정의 (예: "머그컵 수량")
- 시간대·로캘에 따라 달라지는 값은 assertion 대상에서 제외 (주문 일시는 고정 형식 표시)

Page Object는 "무엇을 어떻게 찾는가"만 담고 비즈니스 판단은 테스트 본문에 둡니다. 과도한 추상화는 테스트를 읽기 어렵게 만듭니다.

## 6. 테스트 유효성 검증 (Mutation Testing)

정기적으로 코드를 의도적으로 망가뜨려 테스트가 실패하는지 확인합니다. 도구를 쓰지 않고 수동으로 수행합니다.

| 시점 | 주입 종류 | 결과 |
|---|---|---|
| 중간 점검 | 9종 | 전부 미검출 → 테스트 48개 보강 후 전부 검출 |
| Phase 5 (API) | 8종 | 전부 검출 |
| Phase 6 (E2E) | 6종 | 전부 검출 |

**주입 시 주의:** 원복은 `git checkout --`이 아니라 **작업 전 파일 복사본**으로 합니다. git으로 되돌리면 아직 커밋하지 않은 작업까지 사라집니다(실제로 한 번 사고가 있었고, 그 기록을 [중간 점검 가이드](phase-4-5-review-guide.html)에 남겼습니다).

## 7. CI 파이프라인

```
checkout → Node 22 → npm ci → chromium 설치 → DB 준비 확인
  → Unit(125) → API(73) → E2E(7) → 리포트/증거 업로드
```

- 트리거: Pull Request, main push
- 앞 단계가 실패해도 모든 테스트 레이어를 실행 (`if: ${{ !cancelled() }}`) — 어느 레이어까지 영향받았는지 한 번에 파악하고 E2E 증거를 확보하기 위함
- 하나라도 실패하면 workflow 실패
- 리포트는 항상, 실패 증거(스크린샷·트레이스)는 실패 시에만 업로드 (14일 보관)
- 실측: 성공 시 약 1분

## 8. 현재 범위와 한계

**다루지 않는 것과 그 이유**

| 항목 | 이유 |
|---|---|
| 로그인/인증 | 이 프로젝트의 검증 대상이 아님. `X-User-Id` 헤더로 대체 |
| 결제 연동 | 외부 의존이 생기면 테스트 결정성이 깨짐 |
| 성능/부하 테스트 | 기능 검증에 집중 |
| 크로스 브라우저 | Chromium만. 필요 시 projects 추가로 확장 가능 |
| 접근성 자동 검사 | 접근 가능한 이름은 로케이터 설계로 확보했으나 별도 검사는 미실시 |

**알려진 제약**

- 동시 실행 불가 (DB 단일) — 4장 참고
- 시간 의존 로직 없음 (쿠폰 유효기간 미구현)
